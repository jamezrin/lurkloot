# Merge-First Release Flow Design

## Summary

Applying a `release/*` label to a pull request into `main` currently cuts the release branch, opens a
replacement pull request, and **closes the pull request that was labeled**. The labeled pull request is
never merged; the release branch carries its content to `main` instead.

This design removes that substitution. A labeled pull request is merged normally, like any other. Only
after it lands does the automation cut `release/X.Y.Z` from the new `main` tip, commit the version bump,
and open its own pull request. Merging that second pull request publishes the release, as it does today.

The same change repairs two live defects in the candidate pipeline, both rooted in driving privileged
builds from `pull_request_target`.

## Goals

- Merge a labeled pull request through the normal path; never close it as superseded.
- Derive the release branch from the merge commit on `main`, so its diff is exactly the version bump.
- Keep label-time validation and a published preview candidate.
- Fix preview environment rejections for label-time builds.
- Fix the release pull request never receiving a candidate build.
- Keep GitHub release assets restricted to a known set.

## Non-goals

- Changing version derivation, label semantics, or the one-label-at-a-time rule.
- Changing `release.yml`, the production approval gate, or the `main` → `develop` sync.
- Changing Chrome Web Store submission timing.
- Reviving any workflow from `.worktrees/`.

## Current behavior and why it is wrong

`prepare-release.yml` runs a single `prepare` job on `pull_request_target` `[labeled, unlabeled]`. On a
`release/*` label it cuts `release/$VERSION` from the pull request **head**, pushes it, opens a pull
request, then at lines 118–129:

```yaml
- name: Supersede the triggering pull request
  run: |
    gh pr comment "$TRIGGER" --body "Superseded by $url, ..."
    gh pr close "$TRIGGER"
```

Observed on [#146](https://github.com/jamezrin/lurkloot/pull/146): labeled `release/minor`, closed
unmerged, replaced by [#148](https://github.com/jamezrin/lurkloot/pull/148) (`release/1.6.0` → `main`).

Two problems follow. A label — a piece of metadata, trivially applied and removed — performs an
irreversible action on the pull request it is attached to. And because the release branch is cut from the
head rather than from `main`, its pull request diff contains the whole feature set plus the bump, rather
than the bump alone.

## Defect 1: preview environment rejects label-time builds

Run [29664864450](https://github.com/jamezrin/lurkloot/actions/runs/29664864450) failed. Three jobs —
`extension / finalize`, `site / deploy`, `docker / publish` — each ran 1–2 seconds and recorded **zero
steps**, which indicates rejection before dispatch rather than a build error. The deployments API confirms:

```json
{"environment":"preview","ref":"develop"}
{"environment":"preview","ref":"develop"}
{"environment":"preview","ref":"develop"}
```

The `preview` environment carries a `branch_policy` admitting only `main` and `release/*`. The workflow
runs on `pull_request_target` for a pull request whose head is `develop`, so GitHub resolves the deployment
ref to `develop` and rejects every job declaring `environment: preview`
(`build-release-candidate.yml:104`, `build-docker.yml:98`, `build-extension.yml:133`,
`site-deploy.yml:71`). `gate` then aggregates the three failures and exits 1.

The cache-write warnings in that run (`token has no writable scopes`) are unrelated and are not addressed
here.

## Defect 2: the release pull request never gets a candidate build

`cut` opens the release pull request using `GITHUB_TOKEN`. GitHub does not dispatch workflow runs for
events generated by `GITHUB_TOKEN`, so `release-candidate.yml` never fires for it. Every recent success in
that workflow's history took the `non-release` fast path at line 17, having been triggered by an ordinary
pull request whose head was not `release/*`. The release branch has therefore never actually exercised the
candidate path through this trigger.

## Target flow

```
1. Open develop → main, apply release/minor
2. labeled       → validate policy; build and publish preview candidate
3. merge normally with a merge commit         (pull request stays merged, not closed)
4. closed && merged && has release/* label
                 → cut release/1.6.0 from the merge commit on main
                   commit "chore(release): bump version to 1.6.0"
                   push branch, open pull request → main
                   build the candidate for that branch directly
5. any later push to release/** → rebuild the candidate
6. merge the bump pull request → release.yml publishes
```

Step 4 replaces steps 3–6 of the old flow. Steps 5 and 6 are new only in their trigger, not their content.

## Changes

### `prepare-release.yml`

Split the single `prepare` job in two.

`validate` keeps `types: [labeled, unlabeled]`, the `if` guard at lines 17–20, the policy resolution step,
the orphan-report step, and the `preview` call. It no longer pushes a branch, opens a pull request, or
closes anything. Its purpose is to reject an invalid label combination early and give a testable preview
build.

`cut` is new, on `types: [closed]`, guarded by:

```yaml
if: >-
  github.event.pull_request.merged &&
  github.event.pull_request.head.repo.full_name == github.repository &&
  !startsWith(github.event.pull_request.head.ref, 'release/') &&
  contains(join(github.event.pull_request.labels.*.name, ','), 'release/')
```

It resolves the policy the same way, checks out `github.event.pull_request.merge_commit_sha`, applies the
bump with the existing trusted `prepare-workspace` tooling, then pushes `release/$VERSION` and opens its
pull request. The `release/*` head exclusion is retained so merging the bump pull request cannot recurse.

Delete lines 118–129 entirely.

Retain the "Refuse to overwrite another pull request's release branch" guard, moved into `cut`. Its body
check still matches on `via #$TRIGGER.`, which remains meaningful because the trigger is still the labeled
pull request.

### `preview` environment

Add `develop` and `hotfix/*` deployment branch policies alongside the existing `main` and `release/*`.
`develop` covers the normal flow; `hotfix/*` covers the hotfix flow, which `CLAUDE.md` branches from `main`.

The deployment ref observed in Defect 1 was the head branch name, not a `refs/pull/*` ref, so no wildcard
pull request pattern is required or wanted.

This grants preview credentials — `CRX_PRIVATE_KEY`, `CLOUDFLARE_API_TOKEN`, GHCR write — to code built
from `develop`. The accepted rationale: `prepare-release.yml:19` already restricts these jobs to
same-repository heads, so forks can never reach them, and the trigger is a label applied deliberately by a
maintainer. The residual exposure is a malicious transitive dependency landing on `develop` via Renovate
and executing during install or build inside a credentialed job. This is accepted, not mitigated.

### `scripts/release/repository-config.mjs`

The module currently reconciles the repository patch and two rulesets (`applyRepositoryConfig`, lines
113–132) and has no notion of environments. Add deployment branch policy reconciliation for `preview` so
the four patterns are declared in code rather than set by hand, following the existing
`reconcileRuleset` / `assertRuleset` read-back pattern. Extend `repositoryConfiguration` to report them.

### Candidate build for the release branch

Two paths drive it, because neither alone is sufficient.

**Initial build, from `cut` directly.** After pushing the branch and opening the pull request, `cut` calls
`build-release-candidate.yml` with the pull request number it just created, mirroring how the current
`preview` job at `prepare-release.yml:131-148` is wired. Passing the number explicitly avoids a lookup race
against a pull request created moments earlier in the same job. This runs in the `pull_request_target`
context of the labeled pull request, so its deployment ref is `develop` — admitted by the widened policy.

**Subsequent builds, from a `push` trigger on `release/**` in `release-candidate.yml`.** This covers any
later push to the release branch and is the path that no longer depends on a `GITHUB_TOKEN`-created pull
request event firing. Here `github.ref` is `refs/heads/release/X.Y.Z`, which the existing policy admits.

The `resolve` and `preview` jobs at `release-candidate.yml:40-91` read `github.event.pull_request.*`
throughout and cannot run on a `push` event unchanged. The push path needs every one of those substituted:

| Value | Pull request event | Push event |
| --- | --- | --- |
| `ref` | `pull_request.head.sha` | `github.sha` |
| `trusted_ref` | `pull_request.base.sha` | tip of `main` |
| `version` | label policy | `github.ref_name` minus the `release/` prefix |
| `pr_number` | `pull_request.number` | `gh pr list --head "$ref_name" --base main --state open` |
| labels | `GITHUB_EVENT_PATH` | not read; version comes from the branch name |
| concurrency | `...-${{ pull_request.number }}` | `...-${{ github.ref_name }}` |

The existing "Match the committed release identity" step (lines 63–73) already asserts that the branch name
suffix, the committed `package.json` version, and the resolved version all agree, so dropping label-based
policy resolution on the push path loses no validation.

Keep the existing `pull_request_target` trigger for the `non-release` fast path, which sets the
`release candidate / ready` commit status on ordinary pull requests.

### Release asset allowlist

`cli.mjs publish-candidate` (lines 101–117) globs every file in the assets directory, and `release.yml:186`
uploads `release-assets/*`. Any stray file written into that directory becomes a published asset.

The current asset set is exactly `lurkloot-$version-chrome.zip`, `lurkloot-$version-firefox.zip`,
`lurkloot-$version-firefox-sources.zip`, `lurkloot-$version-chrome.crx`, and `SHA256SUMS`. No current
workflow produces `candidate.json`; the `v1.5.0` release carries one because it was cut under the previous
workflow generation, whose producers now survive only in `.worktrees/`.

Assert the directory contents against that expected set before upload, failing the job on an unexpected
entry. This is what keeps `candidate.json` — or anything like it — from returning.

The stale `v1.5.0` asset is removed manually and out of band:

```
gh release delete-asset v1.5.0 candidate.json
```

## Testing

`scripts/release/workflows.test.mjs` already asserts against workflow structure; extend it to cover the
`validate` / `cut` split, the `cut` guard expression, and the absence of any `gh pr close` in
`prepare-release.yml`. Add `repository-config.test.mjs` coverage for the four `preview` branch policies,
and `cli.test.mjs` coverage for the asset allowlist assertion on both an accepted set and a set containing
an unexpected file.

End-to-end verification requires a real release cycle; `1.6.0` is the first one through this flow.

## Migration

`release/1.6.0` and its pull request [#148](https://github.com/jamezrin/lurkloot/pull/148) already exist,
cut from `develop` under the old flow, and [#146](https://github.com/jamezrin/lurkloot/pull/146) is closed
unmerged. Reconciling that state is a separate decision from this design and is not specified here.

## Amendment, 2026-07-19: the push trigger was removed

The `push` trigger on `release/**` described above was removed after one release cycle. It was added
because a `GITHUB_TOKEN`-created pull request does not fire `opened`, so the release pull request
would never receive its first candidate build. That gap is already closed by `cut` calling
`build-release-candidate.yml` directly with the pull request number it just created.

Every later push to the release branch also fires `pull_request_target: synchronize`, so both
triggers started a build for the same commit. They carried different controller concurrency groups —
keyed on the pull request number and on the ref name — so both were admitted, and only the inner
`release-candidate-${version}` group cancelled one of them. The cancelled run's jobs then surfaced on
the pull request as failing checks, on every release-branch push.

The trigger covered no case that `cut` and `synchronize` do not already cover, so it was deleted
rather than reconciled.
